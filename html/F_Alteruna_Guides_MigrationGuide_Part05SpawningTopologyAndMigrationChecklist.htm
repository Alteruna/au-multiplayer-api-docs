      <h1>Server topology</h1> <p>This is the section that changes how you should think about everything above. Most of these frameworks assume a server tier exists before you write a line of gameplay code; Alteruna makes it a deployment choice you bolt on afterward.</p> <ul> <li><strong>Photon PUN 2</strong> - every peer connects to Photon's cloud; one client is elected Master Client and gets first say on room-level decisions.</li> <li><strong>Photon Fusion</strong> - chosen per session via <span class="c">GameMode</span>: <span class="c">Host</span> (one peer is host+client) or <span class="c">Server</span> (dedicated), both with a single state authority - or <span class="c">Shared</span>, where every peer simulates and state authority can move between them, the one mode here that's actually peer-symmetric like Alteruna.</li> <li><strong>Netcode for GameObjects</strong> - one process is <em>the</em> host or server, chosen at <span class="c">StartHost()</span>/<span class="c">StartServer()</span>. All writes route through it by construction.</li> <li><strong>FishNet</strong> - built dedicated-server-first; host mode (server and client in one process) is supported but treated as the special case, not the default.</li> <li><strong>Alteruna</strong> - peer-symmetric by default, every peer runs identical code. <span class="c">Host()</span> starts a local host for others to join directly; <span class="c">Connect()</span> + <span class="c">CreateRoom()</span> goes through Alteruna's relay with the lowest-index user auto-elected coordinator for tie-breaks; <span class="c">StartRemoteServer()</span> spins up a headless dedicated instance when you need real authority.</li> </ul> <p>Practical takeaway: write gameplay logic as if <em>any</em> peer could be the one running it, then add <span class="c">StartRemoteServer()</span> later if you need server-side validation - do not reach for a "who's the server" check as your first instinct the way you would in host/dedicated Fusion, Netcode, or FishNet.</p> <h1>Bandwidth and update-rate control</h1> <p>Alteruna generalizes what Photon does per-<span class="c">PhotonTransformView</span> into a five-tier LOD system that any <span class="c">Synchronizable</span> or <span class="c">AttributesSync</span> component can opt into: a far-away object can sit in the <span class="c">Low</span> bucket at 10 Hz while a nearby one stays in <span class="c">Max</span> at up to 120 Hz - no separate code path, same <span class="c">Commit()</span> call either way. See <a href="F_Alteruna_Guides_UserGuide_Part02MultiplayerComponent.htm">User Guide Part 02</a> for how Buckets are configured on the Multiplayer Component. Every <span class="c">Sync</span>, <span class="c">BroadcastRemoteMethod</span>, and <span class="c">InvokeRemoteMethod</span> call also takes a <span class="c">Reliability</span> (<span class="c">Reliable</span>/<span class="c">Unreliable</span>) - the same lever as Photon's <span class="c">SendOptions</span>.</p> <h1>Migration checklist</h1> <p>Work top to bottom - each step assumes the previous one is done.</p> <ol> <li>Swap the connection bootstrap: <span class="c">ConnectUsingSettings</span>/<span class="c">StartHost</span>/<span class="c">StartConnection</span> → <span class="c">multiplayer.Connect()</span> (or <span class="c">Host()</span> for a LAN-style session), then <span class="c">CreateRoom()</span>/<span class="c">JoinRoom()</span>.</li> <li>Replace <span class="c">PhotonView</span>/<span class="c">NetworkObject</span> identity with a <span class="c">CommunicationBridgeUID</span>-derived base - <span class="c">AttributesSync</span> for attribute-driven sync, <span class="c">Synchronizable</span> for hand-written serialization, <span class="c">Avatar</span> for the player object itself.</li> <li>Convert <span class="c">[PunRPC]</span>/<span class="c">[ServerRpc]</span>/<span class="c">[ClientRpc]</span>/<span class="c">[ObserversRpc]</span> methods to <span class="c">[SynchronizableMethod]</span>, and their call sites to <span class="c">BroadcastRemoteMethod</span>/<span class="c">InvokeRemoteMethod</span>.</li> <li>Convert <span class="c">OnPhotonSerializeView</span> fields, <span class="c">NetworkVariable&lt;T&gt;</span>, and <span class="c">SyncVar&lt;T&gt;</span> to <span class="c">[SynchronizableField]</span> - or a hand-written <span class="c">Synchronizable</span> where you need byte-level control.</li> <li>Replace ownership checks (<span class="c">IsMine</span>/<span class="c">IsOwner</span>/<span class="c">Owner</span>) with <span class="c">avatar.IsMe</span>/<span class="c">avatar.Possessor</span>, re-anchoring any "am I allowed to act on this" logic around Avatar possession.</li> <li>Wrap any mutation two peers could race on in <span class="c">TryLockResource</span>/<span class="c">UnlockResource</span> - this is new work, not a swap, since no implicit authority is doing it for you.</li> <li>Swap <span class="c">PhotonNetwork.Instantiate</span>/<span class="c">NetworkObject.Spawn</span>/<span class="c">ServerManager.Spawn</span> for a <span class="c">Spawner</span> component's <span class="c">Spawn()</span>/<span class="c">Despawn()</span>.</li> <li>Re-point session callbacks at <span class="c">MultiplayerManager</span>'s <span class="c">UnityEvent</span>s: <span class="c">OnConnected</span>, <span class="c">OnRoomJoined</span>, <span class="c">OnOtherUserJoined</span>, <span class="c">OnOtherUserLeft</span>, <span class="c">OnRoomLeft</span>.</li> <li>Decide topology deliberately: ship peer-symmetric (the default), self-host with <span class="c">Host()</span>, or add <span class="c">StartRemoteServer()</span> for authoritative validation.</li> <li>Tune Bucket behaviors and <span class="c">Reliability</span> per <span class="c">Synchronizable</span> instead of relying on one global tick rate.</li> </ol> <h2>Mental-model shifts to watch for</h2> <ul> <li><strong>There is no implicit "server" to trust.</strong> Any peer can call <span class="c">BroadcastRemoteMethod</span>, <span class="c">InvokeRemoteMethod</span>, or <span class="c">Spawn()</span>. Nothing blocks two peers from doing so at once - that is precisely what <span class="c">TryLockResource</span> is for.</li> <li><strong>Field sync is diffed on <span class="c">LateUpdate</span>, not replicated every network tick.</strong> Unlike <span class="c">NetworkVariable</span>'s automatic dirty-flag replication, batch related <span class="c">[SynchronizableField]</span> writes before the frame ends to avoid sending a torn intermediate state.</li> <li><strong>Ownership lives on the Avatar, not on every synced component.</strong> A <span class="c">Synchronizable</span>/<span class="c">AttributesSync</span> script has no owner field of its own - check the Avatar that logically controls it, or build a possession pattern for standalone objects.</li> <li><strong><span class="c">[SynchronizableField]</span>/<span class="c">[SynchronizableMethod]</span> order is positional.</strong> Declaration order becomes wire index. Reordering members or inserting one in the middle shifts every index after it - treat it with the same discipline as Protobuf field numbers, and append rather than insert.</li> <li><strong><span class="c">BroadcastRemoteMethod</span> and <span class="c">InvokeRemoteMethod</span> are not interchangeable.</strong> The former always includes the sender; the latter defaults to everyone but the sender, and accepts a specific user or list. See <a href="F_Alteruna_Guides_MigrationGuide_Part03RemoteProcedureCalls.htm">Part 03</a> for the full comparison.</li> </ul> <hr/><br/> <a href="F_Alteruna_Guides_MigrationGuide_Part04OwnershipPossessionAndResourceLocking.htm">← Back</a> | <a href="T_Alteruna_Guides_ExampleGameGuide.htm">Next →</a>
