      Remarks

      [DocStyle(reformatRemarks)] <h1>Sessions and connection</h1> <p>All of these frameworks separate "get on the network" from "get into a session together". Alteruna keeps that split too: <span class="c">Connect()</span> reaches Alteruna's relay/matchmaking service, then <span class="c">CreateRoom()</span> or <span class="c">JoinRoom()</span> puts you in a session - closer to Photon's connect-then-join-room flow than to Fusion's or Netcode's single call that starts a <span class="c">NetworkRunner</span>/<span class="c">NetworkManager</span> and joins a session in one step. One difference from all of them: <span class="c">MultiplayerManager</span> connects automatically on start by default (the <span class="c">ConnectOnStart</span> option), so you usually don't call <span class="c">Connect()</span> yourself at all - it's only there for when you've turned that off.</p> <p>The recommended way to get into a room is the <a href="T_Alteruna_Multiplayer_Prefabs_RoomMenu.htm">RoomMenu</a> prefab (see <a href="F_Alteruna_Guides_UserGuide_Part05PackageContent.htm">User Guide Part 05</a>), rather than hand-rolling this. Its Start button is a useful pattern to know regardless: if you're connected to Alteruna's service, create a room there; if not (offline, unregistered, LAN-only build), fall back to hosting locally instead of failing outright.</p>
      C#
      if (multiplayer.IsConnected)

    multiplayer.CreateRoom();

      <p>Session and player events move from interface overrides (PUN 2), C# events (Netcode, FishNet), or <span class="c">NetworkRunner</span> callbacks (Fusion) onto <span class="c">UnityEvent</span> listeners on <a href="T_Alteruna_Multiplayer_Unity_MultiplayerManager.htm">MultiplayerManager</a>:</p>

      <p>See <a href="F_Alteruna_Guides_UserGuide_Part03UserAndRooms.htm">User Guide Part 03</a> for what a User and a Room are in Alteruna terms.</p> <h1>Networked identity</h1> <p><span class="c">PhotonView</span> (PUN 2) and <span class="c">NetworkObject</span> (Fusion, Netcode, FishNet) do double duty: a stable network ID plus a slot for behaviours that opt into replication. Alteruna splits that into a base identity, <a href="T_Alteruna_Multiplayer_Unity_CommunicationBridgeUID.htm">CommunicationBridgeUID</a>, and two ways to attach data to it:</p> <ul> <li><strong><a href="T_Alteruna_Multiplayer_Unity_AttributesSync.htm">AttributesSync</a></strong> - the PhotonView-in-a-script equivalent. Inherit it, mark members with <span class="c">[SynchronizableField]</span>/<span class="c">[SynchronizableMethod]</span>, done.</li> <li><strong><a href="T_Alteruna_Multiplayer_Unity_Synchronizable.htm">Synchronizable</a></strong> - lower level, for when you want to hand-write the byte stream yourself (the <span class="c">IPunObservable</span> equivalent), overriding <span class="c">AssembleData</span>/<span class="c">DisassembleData</span> and calling <span class="c">Commit()</span> on your own schedule. See <a href="F_Alteruna_Guides_DeveloperGuide_Part01CreatingCustomSynchronizable.htm">Developer Guide Part 01</a> for a full walkthrough.</li> <li><strong><a href="T_Alteruna_Multiplayer_Unity_Avatar.htm">Avatar</a></strong> - the player-representing object specifically. A <span class="c">CommunicationBridge</span> that additionally tracks who possesses it, which is where ownership questions actually live (see <a href="F_Alteruna_Guides_MigrationGuide_Part04OwnershipPossessionAndResourceLocking.htm">Part 04</a>).</li> </ul> <h1>State synchronization</h1> <p>The closest thing to a one-line swap in this whole guide: mark a field, stop writing serialization glue.
