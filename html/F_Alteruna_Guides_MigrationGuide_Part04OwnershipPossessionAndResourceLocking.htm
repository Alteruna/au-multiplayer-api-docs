      <p>If a gameplay object other than the player needs an "owner" concept (a vehicle, a held tool), that is a pattern you build on top - commonly by possessing a purpose-built Avatar for it, or by pairing it with resource locking below.</p> <p>One thing worth being precise about: <span class="c">avatar.Possessed(user)</span> is unilateral and client-declared, not arbitrated. Calling it just tells every other peer "this avatar is now possessed by this user" and they apply it on receipt - closer to Photon's <span class="c">OwnershipTransfer.Takeover</span> mode than to <span class="c">Request</span> mode, and with no equivalent to Netcode/FishNet's server-only <span class="c">ChangeOwnership</span>/<span class="c">GiveOwnership</span>. If two peers could plausibly call <span class="c">Possessed()</span> on the same avatar at once, that race isn't resolved for you - see resource locking below.</p> <h1>Resource locking</h1> <p>Worth being precise about the framework side too, since "server-enforced" doesn't apply evenly across them. Netcode's <span class="c">ChangeOwnership</span> and FishNet's <span class="c">GiveOwnership</span> can only be called by the server/authority, so ownership changes there are genuinely gated by a single decision-maker - there's just no general-purpose lock for <em>arbitrary</em> resources, only for object ownership. Photon PUN 2's <span class="c">RequestOwnership()</span> is not server-enforced at all: with <span class="c">OwnershipTransfer.Request</span>, Photon relays the request to the <em>current owner's client</em>, and that client's own <span class="c">OnOwnershipRequest</span> callback decides whether to grant it - Photon's servers just track who's registered as owner, they don't arbitrate. With <span class="c">OwnershipTransfer.Takeover</span> there's no negotiation at all. Fusion's host/dedicated-server modes gate ownership the same way Netcode does; Shared Mode gives you authority transfer but, like the others, no request/deny handshake for an arbitrary shared resource.</p> <p>Alteruna's <span class="c">TryLockResource</span> is a genuine arbitrated queue, not a client-side declaration: the request is handled by whichever peer is host (locally if you are the host, relayed there otherwise), which grants the lock to whoever's next in a real FIFO queue and tells everyone else to wait. That makes it closer in strength to Netcode/FishNet's server-gated ownership than to Photon's owner-negotiated <span class="c">RequestOwnership()</span> - but usable for any resource, not just tied to who owns a whole networked object. Request a lock, get told yes or no, release it when you're done.</p>
